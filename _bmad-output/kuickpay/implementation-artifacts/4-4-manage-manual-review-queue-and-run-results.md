# Story 4.4: Manage Manual Review Queue and Run Results

Status: ready-for-dev

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a finance operator,
I want a focused Manual Review queue and reconciliation run summaries,
so that unsafe records are visible and actionable without mixing them with normal paid records.

## Acceptance Criteria

**AC1 — Manual Review queue (UX-DR16, FR26)**
**Given** Manual Review Vouchers exist
**When** staff open the Manual Review queue or filter
**Then** rows show reason summary, client, invoice, amount, Consumer Number, last inquiry time, and next allowed action
**And** the queue shows only `manual_review` vouchers (it never mixes in `posted`/normal records)
**And** an empty queue renders a localized no-results message, not a broken table.

**AC2 — Reconciliation run summaries (UX-DR17, FR22, FR24)**
**Given** a reconciliation run completes
**When** staff review the run summary
**Then** it shows run type, status, the per-run counts, timestamps, and failure class
**And** counts are rendered from the durable `kuickpay_reconciliation_runs` counters with accurate labels (no fabricated counters, no double-counting in the visible labels)
**And** no secrets, raw SOAP, or credentials appear anywhere in the run views.

**AC3 — Exception drill-down (UX-DR16, NFR8, NFR9)**
**Given** an unmatched, duplicate, mismatched, malformed, underpaid, overpaid, or late case exists
**When** staff drill into it
**Then** the detail view provides sanitized evidence and allowed next actions
**And** it never presents direct paid-state shortcuts (no Force Paid / Mark Paid; success styling only for `posted`).
**And** the run-detail surface covers BOTH evidence surfaces honestly: (a) **matched** transitions (mismatched / malformed / underpaid / overpaid / late, and any matched `manual_review`) carry a `kuickpay_reconciliation_items` row and drill into the voucher detail page (4.2) where the gated next actions live; (b) **audit-only bulk exceptions** — `unmatched` (no local voucher) and the duplicate-echo (`evidence.duplicate`) — write **no** item row (Epic-3 design: `KuickPayReconcileService` increments the counters then `continue`s on an audit event), so they are surfaced from the run-scoped audit events as sanitized, redacted rows: a `duplicate` row links to its voucher detail (it has a `voucher_id`); an `unmatched` row has no `voucher_id`, so it renders evidence only — no voucher link and no next action. The run summary's Unmatched count therefore always has a corresponding per-row evidence entry, never a count with no drill-down (see Dev Notes → Audit-only bulk exceptions).

**Derived / non-negotiable acceptance criteria**

- **AC4 (company scope):** Every read is scoped to the authenticated staff company. `company_id` is resolved server-side (`(int) $this->company_id`), never from request input. A run id or voucher id outside the staff company resolves to a safe not-found redirect and never renders another company's data. `kuickpay_reconciliation_items` has **no** `company_id` column, so item reads are gated by first loading the parent run via a company-scoped fetch (see Dev Notes → Company-scoping the items table).
- **AC5 (read-only surfaces):** The two new controllers (`admin_manual_review`, `admin_reconciliation`) are GET-only and perform no writes, no SOAP, no state transition, and no posting. All mutations remain on the existing `admin_vouchers` action endpoints from Story 4.3. Adding a GET route that mutates state is an explicit anti-pattern (architecture.md#Anti-Patterns).
- **AC6 (next allowed action authority):** Per-row "next allowed action" is computed from `KuickpayVouchers::ALLOWED_ACTIONS_BY_STATE` (the single source of truth) and gated by the existing per-action permission check `staffGroupAllows('<action>')`. No new state machine is invented. The queue links each case to the existing `admin_vouchers/detail/{id}/` page where the gated 4.3 action forms live; it does not re-implement the mutating POST handlers.
- **AC7 (presenter / closed-allowlist discipline):** New run-type and run-status labels/badges go through pure presenter allowlists with safe fallbacks. A raw DB value is never concatenated into a language key. New presenter maps are unit-tested against a model-owned source of truth.
- **AC8 (deferred items absorbed):** The two LOW deferred items this story explicitly inherits are resolved. The bulk run-summary count model is **decided in this story, not delegated to the dev** — Dev Notes → Count model decision gives the exact labels/formula applied identically in list + detail. Bulk `run_date` is bounded ≤ today with a max look-back, surfaced through a concrete error contract (Task 7). See Dev Notes → Deferred work absorbed.
- **AC9 (no schema migration required for the core):** The `kuickpay_reconciliation_runs`, `kuickpay_reconciliation_items`, and `kuickpay_vouchers` tables already exist and already carry every field these views read. Do not add tables or columns. The only plugin lifecycle change is the version bump that re-syncs nav + ACL.

### Company-scoping the items table (AC4 — critical)

`kuickpay_reconciliation_items` has no `company_id`. A naive `WHERE run_id = ?` would let a crafted `run_id` from another company leak items. Two layered guards (do both):
1. In the controller, fetch the run first via `KuickpayReconciliationRuns->getForCompany($run_id, $company_id)`; if it returns `false`, redirect to the run list with a not-found message and `return` before touching items.
2. In `getByRun()`, still JOIN `kuickpay_reconciliation_runs` and filter `kuickpay_reconciliation_runs.company_id = ?` (defense in depth — the model method must be safe on its own).

This mirrors the established `AdminVouchers::detail()` pattern (company-scoped `getForCompany` + safe not-found redirect).

### The count model decision (AC2, AC8 — resolves `deferred-work.md:118`)

AC2 / UX-DR17 lists ideal columns "checked, posted, unmatched, failed, skipped, Manual Review". The durable model built in Epic 3 (already approved) stores: `total_eligible, total_checked, total_confirmed, total_retry, total_manual_review, total_expired, total_failed, total_errors, total_unmatched`. Reconcile that honestly — **do not invent counters or migrate schema**.

**Resolved display formula (decided in this story; identical in list + detail; labels only):**

| Label | Value |
|---|---|
| Checked | `total_checked` |
| Confirmed (ready to post) | `total_confirmed` |
| Manual Review (incl. unmatched) | `total_manual_review` |
| — of which Unmatched | `total_unmatched` (indented subset, **not** added on top) |
| Failed | `total_failed` |
| Errors | `total_errors` (shown beside Failed, **never summed** — see note) |

Footnotes (Task 5 keys): posting-is-separate, unmatched-is-a-subset, eligible-counts-returned-rows. Field-by-field rationale:

- **checked** → `total_checked`. **Manual Review** → `total_manual_review`. **unmatched** → `total_unmatched`. **failed / errors** → show `total_failed` and `total_errors` as **two separate figures, never summed**. They are disjoint per row (an errored voucher returns its prior status, never `failed`), **but** a wholesale bulk transport/parse failure (`isBulkRunFailure()` true, `KuickPayReconcileService` bumps both `total_failed++` and `total_errors++` for the *same* incident) means a sum would render `2` for one failure. From the stored scalars the view cannot disentangle that overlap, so present them side by side (`count.failed` / `count.errors`) with the `footnote.failed_errors` note — never add them.
- **posted** → there is **no per-run posted counter**. Posting runs on a *separate* cron task (`post_confirmed` → `KuickPayPostingService::postConfirmed`) that does not open a reconciliation run. Display `total_confirmed` labeled "Confirmed (ready to post)" and add the localized footnote that posting is a separate task. Per-voucher posting visibility already exists on the 4.2 voucher detail page (status `posted` + `posting.*` audit events). Do not fabricate a posted column.
- **skipped** → run-level skips (lock held / provider unavailable) typically return before a run row is persisted, so there is nothing to list; persisted runs carry status `running|completed|aborted|failed`. Represent run-level outcome via the `status` badge (`aborted`/`failed`), not a per-voucher skipped counter. There is no per-voucher "skipped" tally.
- **failure class** → at the run level, the `status` badge (`failed`/`aborted`) plus the error counts; at the **item** level (run detail), the per-item `error_class` mapped through `presenter->errorClassLabelKey()` is the precise failure class, and each item links to the voucher detail for full sanitized evidence (this is also the AC3 drill-down).
- **`total_unmatched` vs `total_manual_review` overlap — RESOLVED (do not re-decide):** on bulk runs an unmatched row increments **both** counters (`KuickPayReconcileService` calls `countOutcome(..., 'manual_review', ...)` then `total_unmatched++`), so `total_manual_review` already **includes** unmatched. **Decision:** present Manual Review as the inclusive figure with Unmatched as an explicit indented **subset**, never added on top — `Manual Review (incl. unmatched) = total_manual_review` and `— of which Unmatched = total_unmatched`. This is the most truthful to the stored counters and needs **no arithmetic in the view** (do NOT compute `manual_review − unmatched`; subtraction could break if counter semantics shift). Apply identically in `admin_reconciliation.pdt` and `admin_reconciliation_detail.pdt` with the `footnote.unmatched_subset` note. Labels only — never alter the Epic-3 counters.
- **`total_eligible` semantics:** on bulk runs `total_eligible` counts returned provider rows, not local eligible vouchers (unlike single/cron runs). Add a localized note so operators don't misread it.

### Audit-only bulk exceptions (AC3 — why the items table alone is not enough)

The run-detail items table reads `kuickpay_reconciliation_items`, which only gets a row for **matched, processed** vouchers (the bulk loop calls `itemRepository->record(...)` only after `persistEvidence`). Two bulk outcomes write **no** item row — they bump counters and `continue` on an audit event instead:
- **Unmatched** (`evidence.unmatched`): the provider echoed a Consumer Number with **no** local pending/retry voucher. There is no `voucher_id` — nothing to link to, no next action. Without surfacing the audit row, the run's `total_unmatched` count would have **no** drill-down evidence (the AC3 gap this story closes).
- **Duplicate echo** (`evidence.duplicate`): the provider echoed the same Consumer Number twice in one run; the first occurrence already has an item row + voucher detail, so reprocessing is skipped. The duplicate is audit-only **but carries a `voucher_id`**, so it can link to that voucher's detail (whose 4.2 audit history already shows the `evidence.duplicate` event).

So AC3 is satisfied by **two** surfaces: matched exceptions drill into voucher detail via item rows; unmatched/duplicate are read from `KuickpayAuditEvents->getByRun()` and shown as sanitized rows (redacted `payload` blob + trace id), with a voucher link only when `voucher_id` is present. The presenter already maps both event names (`eventLabelKey`). (Note: `evidence.duplicate` covers both same-run duplicate echoes and already-non-pending reruns — both are intended audit-only rows, and the one "Duplicate" label fits both.) This adds a **read method only** — no schema change, and **no new audit events** (4.5 owns adding events; 4.4 consumes the existing 17-event allowlist).

**Whole-run bulk failures are NOT per-row drill-down cases (AC3 boundary).** When the provider response fails wholesale — `isBulkRunFailure()` true (run-level `timeout` / `transport_error` / `malformed_response`) — `runBulk()` marks the run `failed`, bumps Failed + Errors, and returns **before** the per-row loop, so there is **no** item row and **no** `evidence.unmatched` / `evidence.duplicate` row to show, by design. This case is represented at the **run level** by the `failed` / `aborted` status badge + the Failed/Errors figures (that is AC2's run-level "failure class"), not by an items/audit drill-down row; the detail view's `no_items` / `no_audit_exceptions` empty states correctly cover a failed run with zero rows. AC3's per-row "malformed" drill-down applies to per-row malformed evidence on a *matched* voucher (which does write an item row). Do **not** invent a per-row writer for the wholesale-failure path — that is Epic-3 scope, and this story adds no writers.

**Index tradeoff (accepted under AC9).** `kuickpay_audit_events` is indexed on `company_id` / `voucher_id` / `event_name`, **not** `run_id`. `getByRun()` is company-scoped (indexed) + bounded at 500 and run-detail is not a hot path, so the `run_id` filter resolving after the company narrow is an accepted tradeoff that keeps AC9's "no schema migration." A composite `(company_id, run_id, event_name)` index is a deferred optimization if audit volume grows — call it out, do not add it here.

### Shared presenter language namespace (gotcha)
