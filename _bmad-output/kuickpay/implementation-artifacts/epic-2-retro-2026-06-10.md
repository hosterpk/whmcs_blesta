## 2. What Went Well

- **The pure-helper / protected-seam testability pattern scaled to the whole epic.** Every story extracted DB-free, harness-drivable seams: `expandPattern()` + injected `randomInt()` (2-2), Guard-A/B idempotency via a fake SOAP client (2-3), `displayVoucherForContext()`/`createVoucherForContext()` and the service-owned `requestMatchesVoucher()` comparator (2-4), `customerVoucherStatusDisplay()`/`resolveDisplayMode()` via `expose*` subclasses (2-5), `enabledInstructionGroups()`/`customerStatusCheckSupported()` (2-6). This is the single move (carried from Epic 1's `currencyEligible`/`maskCredentials`) that made a DB-less epic verifiable.
- **Idempotency was treated as a first-class design problem at the mutation surface (2-3).** Two explicit guards — Guard A (never re-issue the same row) and Guard B (`getLatestByInvoiceId()` + a fail-closed reload decision matrix) — instead of a naive `pending && no reference` check that would double-issue after a timeout.
- **Fail-closed discipline held where it mattered most.** 2-3's two real review findings were both fail-*open* defects (epoch `01-Jan-70` dates; a broad `catch(Throwable)` re-persisting a fabricated `transport_error` over a recorded success) — caught and fixed to fail closed. 2-1 gated voucher creation behind `if (!$this->Input->errors())` because `buildProcess()` sets errors but does not early-return.
- **One owner per output surface.** `resolveDisplayMode` owns `display_mode`; `customerVoucherStatusDisplay` owns presentation; `requestMatchesVoucher` is the single comparator for reuse and display. Eliminated cross-layer drift.
- **DB-sourced values never build language keys** — a closed allowlist helper with a neutral default, applied consistently 2-4 → 2-5 → 2-6 (prevents input-driven key lookup / XSS-adjacent footguns).
- **Adversarial review stayed high signal-to-noise.** ~65 findings dismissed as noise/by-design across the epic with clear rationale; only the real defects survived to patch. The Acceptance Auditor independently re-confirmed all ACs on every story.
- **The deferred-work ledger matured into the project's strongest artifact.** Every deferral records origin, file path, reason, severity, **and a named consumer story** — e.g. the concurrency residual is traced 2-2 → 2-3 → 2-4 → the `context_key` schema change; the 3-4 null-paid-date item is tagged "must resolve before 3.5." This directly honors Epic 1 Action Item 4.

## 3. What Was Challenging (cross-story patterns)

- **Pattern #1 — Zero live verification, 6 of 6 stories. The Epic 1 critical-path gate was not built.** Epic 1 retro Action Item 1 ("stand up a real PHP 8.2 + Blesta/MySQL verification path **before Epic 2 schema work merges**") was **not done**. Every Epic 2 story shipped on `php -l` (run on PHP **8.3.31**, target **8.2**) + component PHPUnit 8.5 + fixtures/stubs. The first schema (2-1), first live SOAP mutation (2-3), gating logic (2-4), and all customer-facing rendering (2-5/2-6 `.pdt`) were verified by code inspection only. DB-level unique-key enforcement, the reload-reuse (AC2) flow, audit writes, `ext-soap`, clipboard/responsive UI — all runtime-unverified.
- **Pattern #2 — The concurrency/idempotency "baton" passed three times and still has not landed.** 2-2's secure random prefix removed 2-1's deterministic unique-key race guard → concurrent same-invoice submits now mint two distinct references. 2-3's two-read window can clobber an issued reference (HIGH, accepted deferral). 2-4's Task 9 (schema-level `context_key`/`active_context_key` unique key, architecture.md:351) was **explicitly re-deferred for lack of architect sign-off**. The only durable fix is a schema story that has not been written.
- **Pattern #3 — A spec can be followed exactly and still ship a defect.** 2-6's instructions said "enter the Consumer Number shown above," but a payable voucher can have an empty `consumer_number` (independent column from `kuickpay_reference`; the payable gate keys on `reference()` alone). The implementation was **spec-compliant** (Task 2 forbade gating on consumer number) yet produced a UX mismatch — surfaced as decision-needed, and Israr chose to gate the block on `$has_consumer_number` (commit `8cf7a3b7`). 2-5 had the analogous raw-date-echo miss (fixed to `d-M-y`, `31d7e27e`).
- **Pattern #4 — Blesta footguns keep surfacing at each new layer.** 2-1 hit a fresh cluster at the schema/model layer: `Gateway::$gateway_id` is `private` with a setter but **no getter** (reflection forbidden → shadow into `protected $kuickpay_gateway_id`); `Record->insert()` does not return the new id (must call `lastInsertId()`); `Record->fetch()` returns a **`stdClass`**, not an array; model error language keys must live in **per-model** files the base model auto-loads. None were pre-documented (Epic 1 Action Item 7, the footgun dev note, was not written).
- **Pattern #5 — One comparator, two row shapes.** 2-4's `requestMatchesVoucher()` had to serve both associative arrays from `flatten()` (reuse path) and `stdClass` from `getWithInvoices()` (display path); without explicit `(array)$link` shape-tolerance and a links-conditional rule, every `allow`-mode reload falsely flagged "amount changed." A real iteration cost (red-then-green) in Tasks 6–7.

## 4. Key Insights

1. **Verification debt is no longer a scaffold-era footnote — it is now the dominant accumulating risk.** Epic 1 could defer live verification because it had no mutation surface. Epic 2 removed that excuse (schema, SOAP issuance, gating, customer views) and shipped anyway on lint+stubs. Epic 3's 3-1…3-5 — including the **money-moving posting service (3-5)** — were built interleaved on the *same* lint-only basis. Two of the three highest-risk surfaces in the whole project (mutation, posting) now sit on top of zero DB/runtime verification.
2. **The deferral discipline is excellent and the deferrals are honest — but discipline cannot substitute for the schema work it keeps pointing at.** The concurrency residual is perfectly documented and perfectly unbuilt. A well-tagged HIGH-severity deferral is still a HIGH-severity gap.
3. **The 3-layer review + human-in-the-loop is catching the right class of bug** (fail-open at the boundary; spec-vs-copy mismatch). It is *not* a substitute for a DB/browser — every "coverage gap" in every story is precisely the runtime path the harness cannot drive.
