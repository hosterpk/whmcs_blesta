WebNIC Registrar Module for Blesta — Validation Report

_bmad-output/webnic/planning-artifacts/research/research-prd-webnic-blesta-registrar.md
Fair

This is a strong, unusually well-grounded brownfield capability spec. It has a real thesis — de-risk the migration by mirroring the proven LogicBoxes module first, then layer differentiators in Sections 2–3 — and §4's API findings (token/JWT auth + IP allowlist, no webhooks → polling, contact-handle + registrant-account prerequisite model, the specific pricing shape) are load-bearing: each drives a named FR. Structure, glossary, NFRs, and personas are largely earned, not furniture. The shape is correct for a single-integration registrar module against a fixed framework contract.

Two reviewers disagreed on the single most important claim, and direct code inspection settles it against the PRD. The rubric walker certified §6 as “verifiably accurate against the shipped logicboxes module”; on inspection that certification holds only for the abstract RegistrarModule contract and the config.json feature flags — not for what the concrete module actually does. The shipped logicboxes.php overrides almost none of the domain-centric methods §6 lists (registerDomain, transferDomain, getDomainContacts, lockDomain, sendEppEmail…); it does the real work in addService() / renewService() and the tab* methods. And it ships URL/email forwarding and DNSSEC tabs to clients today (getClientServiceTabs registers tabClientForwarder unconditionally and tabClientDnssec whenever dns_management is on — and it is), which the PRD defers to Section 2 while still promising “0 capability regressions vs LogicBoxes at MVP.” That is a black-and-white self-contradiction.

None of this breaks the PRD — the FR substance is mostly sound and every issue is fixable from information the document already contains — but four High-severity items must be resolved before it is safe to drive architecture and epics: (1) re-derive the parity matrix and Goal G1 from the module's actual overridden surface; (2) decide forwarding/DNSSEC in-or-out and stop promising zero regression if they're out; (3) promote the net-new async pending-order/reconciliation subsystem to a first-class feature with WHAT-level failure-path acceptance criteria; and (4) specify the lost-response-after-submit recovery path for the irreversible, money-spending registration call. Hence the overall grade of Fair.

Decision-readiness

adequate

A decision-maker can mostly act on this: the release-section split (§1.1, §5) is stated as a decision rather than floated, each section is asserted independently shippable, and the Open Questions are genuinely consequential rather than rhetorical. It drops from strong to adequate because the two artifacts an architect would act on first — the §6 parity matrix (explicitly “the definition of feature parity for Section 1”) and §11 — are not yet safe to act on literally: the matrix measures against the abstract contract while labeling it “LogicBoxes behaviour,” and MVP-gating questions sit un-flagged beside deferrable ones.

high

Parity matrix & Goal G1 measure against the abstract contract, not the shipped module

§6; G1
Verified by inspection. logicboxes.php overrides only checkAvailability, getRegistrationDate/getExpirationDate, getServiceDomain, getTlds/getTldPricing/getFilteredTldPricing, getDomainNameServers/setDomainNameservers, plus addService/renewService/suspendService/unsuspendService/cancelService/changeServicePackage and the tab* methods. The matrix rows for registerDomain, transferDomain, renewDomain, restoreDomain, getDomainInfo, getDomainContacts/setDomainContacts, getDomainIsLocked/lockDomain/unlockDomain, sendEppEmail, updateEppCode are abstract-base defaults LogicBoxes never overrides — it performs that work inside addService/renewService and the tabs. An architect who builds WebNIC by implementing those discrete methods will produce a module shaped unlike LogicBoxes, and G1's success signal (“every LogicBoxes registrar method has a working WebNIC equivalent”) is unverifiable as written.
Fix: Re-derive §6 from the module's actual overridden surface; for each row state whether the behavior lives in addService/renewService, in a discrete contract method, or is an abstract-default you are choosing to upgrade (net-new) vs match. Reword G1 to reference observable end-to-end flows, not a method inventory. (Designing WebNIC around the modern domain-centric contract is a defensible improvement — just stop calling it “LogicBoxes behaviour.”)
medium

MVP-blocking open questions are mixed with genuinely deferrable ones

§11 OQ2/OQ4/OQ5/OQ6/OQ8 vs OQ7
OQ4 (contact-handle reuse policy) and OQ5 (registrant-account provisioning) determine the data model and the whole contact-orchestration subsystem behind FR14; OQ6 determines the async state machine; OQ2 (auto-renew) determines renewal correctness (FR23/FR40); OQ8 governs irreversible deletion (FR26). Listing them alongside OQ7 (TLD coverage, genuinely deferrable) flattens the risk.
Fix: Split §11 into “Blockers — must resolve before architecture” (OQ2/OQ4/OQ5/OQ6/OQ8, plus OQ1 schema confirmation) and “Deferrable” (OQ3 mostly, OQ7), and bind each blocking FR to the question that gates it.

Substance over theater

strong

The content is earned. §4 is the genuine spine — every finding carries an explicit “Implication (requirements)” line and maps to a named FR (FR5, FR39, FR14, FR7). The PRD is candid that the MVP is deliberately un-novel and reserves differentiation for later, which is honest framing rather than manufactured novelty. Personas are lean (four) and each surfaces in requirements; NFRs mostly avoid boilerplate (NFR1 ties to Blesta encrypted module-row fields, NFR7 pins PHP 8.2). No findings rise above the done-ness and security items captured elsewhere.

Strategic coherence

strong

Clear parity-first thesis with differentiation explicitly sequenced behind it; prioritization follows the thesis, not implementation ease. Success metrics are outcome-oriented (no vanity DAU/MAU tell). The one structural crack is an internal contradiction: the “0 regressions vs LogicBoxes” metric is falsified by the PRD's own decision to defer forwarding and DNSSEC — both of which the baseline ships today.

high

MVP drops capabilities LogicBoxes ships today, contradicting the “0 regressions” metric

§7.2 FR45/FR46; §6; §12
Verified by inspection. getClientServiceTabs registers tabClientForwarder (URL + email forwarding) unconditionally, and tabClientDnssec + tabClientDnsRecords whenever dns_management is enabled — and config.json sets dns_management: 1. So both forwarding and DNSSEC are in LogicBoxes' default client experience. The PRD defers URL/email forwarding (FR45) and DNSSEC (FR46) to Section 2, yet §12 targets “Capability regressions vs LogicBoxes at MVP: 0.” A LogicBoxes→WebNIC migrator on the MVP would lose both tabs. The WebNIC endpoints exist (Get/Add/Remove Zone URL/Email Forwarding, Check DNSSEC Supported, Get/Update/Delete DNSSEC), so this is a scoping decision, not a capability limit.
Fix: Either pull forwarding (URL + email) and DNSSEC into Section 1 to honor parity, or keep them in Section 2 but delete the “0 regressions” claim and list them explicitly as accepted MVP regressions in §2.3/§12 with operator sign-off. Do not ship both the deferral and the zero-regression promise.
low

No counter-metrics paired with success metrics

§12 quantitative targets
A ≥99% provisioning-success push could be gamed by aggressive retries that inflate API load or risk double-submission; nothing bounds that.
Fix: Add a guardrail metric — e.g. “reconciliation cron stays within N minutes / M API calls per cycle” or “0 services flipped to a wrong terminal state on transient failure” (NFR5 already states this as a quality bar — surface it as a metric).

Done-ness clarity

thin

This is the weakest dimension and the one story creation leans on hardest. Many FRs are concrete and testable (FR2 named env toggle + base URLs, FR7 exact pricing target shape, FR17 explicit pending-vs-immediate branching). But the load-bearing async/idempotency FRs — exactly where bugs cost real, irreversible money — are the ones most reliant on untestable adjectives, and §12's only numeric targets are self-labeled “illustrative,” so the binding acceptance bar is softer than the PRD's parity claims imply. A PRD legitimately defers mechanism to architecture; the gap here is missing WHAT-level acceptance for the failure paths.

high

Net-new async pending-order/reconciliation subsystem lacks failure-path acceptance criteria

§4.2; FR17/FR21/FR39; OQ6
Verified by inspection. LogicBoxes is fully synchronous — no cron() method, no pending-order table, no polling — so this stateful subsystem (durable order/transfer state, scheduler, idempotent finalization, failure transitions) is net-new, yet §6 checks it off as “parity.” FR39 says “finalises or fails” but never defines when a stuck pending becomes failed (timeout, max attempts, backoff), what the client sees for a never-resolving service, whether Blesta keeps invoicing/renewing it, or whether the module owns its own cron vs piggybacks Domain Manager sync. OQ6 admits the timeout/give-up is undecided — and ships it as a checked parity item anyway.
Fix: Name the subsystem net-new. Add FRs specifying the service state machine and legal transitions; per-order poll cadence, max attempts, backoff, and hard timeout; the terminal give-up state + operator alert; client-facing presentation of a long-pending domain; whether renew/cancel are allowed while pending; and concrete persistence (a defined table with install/upgrade artifacts, not “if needed”). Promote OQ6 to a blocker.
high

Idempotency / lost-response recovery is asserted, not specified — the irreversible-money path

FR18; NFR4; G2; (with H3)
FR18's “idempotent and payment-safe … durable local state + uniqueness” is a slogan with no dedup key, no idempotency token, and no “check pending order by domain before re-submitting” step. With async register and no webhooks (§4.2), the dangerous window is concrete: submit register, the HTTP call dies before pendingOrderId is persisted, Blesta retries addService, and a second irreversible registry order is created. The PRD also never evidences that Get Pending Order Info can be queried by domain (vs only by a pendingOrderId you may have lost) — without which lost-response reconciliation is impossible.
Fix: Add an FR for “recover from lost-response-after-submit”: write a registration-intent row keyed by service+domain in its own committed transaction before the API call; on retry, query WebNIC for an existing pending/active order on that domain before ever calling register again; define behavior when the result is unknown (reconcile-by-query, never blind-resubmit). Confirm by-domain pending lookup exists in OTE; if it doesn't, escalate to Critical. Separate “duplicate registration” (module) from “duplicate charge” (Blesta invoicing) so the metric is attributable.
medium

Adjective-bound FRs without measurable acceptance criteria

FR4/FR9/FR11/FR19/FR29/FR41; NFR6
“efficiently,” “degrades gracefully,” “clear,” “actionable,” “the same way they do for LogicBoxes,” “without corrupting service state,” “expected latency” recur on FRs that QA and the dev agent will each interpret differently.
Fix: Replace each with a bound/observable — e.g. FR11: “bulk check of N domains issues ≤ ceil(N/batch) calls; on any batch error the remaining domains are checked individually and returned with per-domain status.” Define the FR41 retryable-vs-terminal error taxonomy once and reference it.
medium

Auth/EPP codes absent from the redaction policy

NFR1; NFR9; FR33
NFR1 redacts “secret/password” and tokens but not EPP/auth codes, which are hijack-grade secrets — leaking or logging one can enable a domain takeover. FR33 introduces send/reset auth-code flows with no storage/expiry/redaction spec.
Fix: Add EPP/auth codes (and arguably order identifiers) to the NFR1/NFR9 redaction list; require they are never logged and never persisted in cleartext, with defined error handling on the reset/send flows.
medium

Quantitative success metrics self-labeled “illustrative”

§12
Marking the only numeric targets non-binding undercuts the acceptance bar for an MVP otherwise pitched as a precise parity contract, leaving the qualitative bullet list + parity matrix as the real gate.
Fix: Either commit the numbers as MVP exit criteria, or move them to a clearly separate “post-launch monitoring” goal so the MVP acceptance set is unambiguous.

Scope honesty

adequate

Omissions are openly stated — §1.3, §10, §2.3, and “➕ Section 2” markers — and the de-scoping is honest in intent (the PRD holds the MVP to parity even though WebNIC could exceed it). It lands at adequate rather than strong for two reasons: the openly-deferred forwarding/DNSSEC nonetheless contradict the parity promise in effect (see Strategic coherence), and the load-bearing §4.3 contact-model assertions are stated as firm fact while resting on an unverified source.

medium

Contact-handle / registrant-account model is load-bearing but unevidenced

§4.3; FR14/FR15; OQ4/OQ5
The “pre-created contact handles + registrantUserId + ≥2 pre-registered hosts” order model is asserted from endpoint names only; nothing quotes a source confirming registration is blocked without pre-registered hosts, or that handles are reusable, or the reuse scope. If WebNIC accepts inline contact data the whole orchestration subsystem is over-engineered; if it's stricter, the design under-delivers.
Fix: Mark §4.3 as unverified-against-a-quotable-source; gate FR14/FR15 on OTE confirmation; resolve OQ4 (reuse policy) and OQ5 (registrant-account provisioning) before freezing those FRs, since they drive table design, cleanup, and privacy exposure.
medium

Missing the BMAD inline assumption/non-goal/note tags

whole doc; cf. §11
Assumptions live only in a prose list and scope deferrals only in table cells, so there is no inline-to-index roundtrip and downstream tooling can't source-extract them. The substance is honest; the machine-extractable tagging the rubric expects is absent.
Fix: Tag the strongest inferences inline where they bite — e.g. [ASSUMPTION: Domain Manager v2.x present] at FR9, [NOTE FOR PM] at FR14's handle-reuse choice (OQ4) — and keep §11 as the index.

Downstream usability

adequate

This PRD is chain-top (it feeds architecture and story creation), and it does several things well: clean unique FR IDs, §9 pre-sketches the file layout, and most domain nouns are defined in §1.4 and used consistently. Weaknesses are real but mechanical — the §6 framing risks pointing architecture at the wrong reference surface (see Decision-readiness), the Domain Manager contract is assumed rather than inspected, and a few terms drift outside the glossary.

medium

Domain Manager contract and version assumed, not verified

FR9; NFR7; Assumption 2
The pricing-import/availability/storefront story (FR6–FR9, G3) hangs on the plugins/domains contract, but the PRD never inspects it to confirm how a registrar module's pricing/availability are consumed, the expected pricing array shape, or the sync hooks. “v2.x” is asserted without evidence from the checkout.
Fix: Inspect plugins/domains in this checkout; pin the real version; make FR9 reference concrete plugin hooks and the exact pricing shape rather than “operate the same way as LogicBoxes.”
medium

“Child nameserver / glue record / host object” used as undefined synonyms

FR15, FR31; §6
Three terms for overlapping concepts with no glossary anchor; architecture must guess whether WebNIC “host” objects and Blesta glue/child-NS are one mechanism.
Fix: Add a §1.4 entry mapping the WebNIC “host” object to Blesta's child-nameserver/glue concept, and use one term consistently.
low

“ID protection” vs “WHOIS privacy” vs “proxy” not disambiguated

§1.4; FR16/FR34/FR48
Treated as near-synonyms in MVP, but FR48 (Section 2) splits “proxy subscription” from “WHOIS privacy” — the relationship isn't pinned up front.
Fix: Add a glossary line distinguishing privacy (WHOIS redaction) from proxy (registrant substitution), and which maps to Blesta's id_protection flag.

Shape fit

strong

Correctly shaped. A brownfield single-integration registrar module against a fixed framework contract calls for a capability-spec shape (parity matrix + FR list + technical-constraint findings), and the absence of User Journeys is appropriate, not a defect — there is no multi-stakeholder UX arc to model; the “journey” is the registrar contract itself. New-vs-existing is cleanly distinguished and §9 is explicitly “non-binding guidance” so it doesn't over-formalize decisions the architect should own. Note the one factual carve-out: the parity-method framing issue (Decision-readiness) is separate from shape — the shape choice itself is right.

Adversarial review

review-adversarial-general.md

The adversarial pass argued the PRD “reads well but rests on a false parity premise.” It raised 22 findings (5 Critical, 6 High, 6 Medium, 5 Low). Adjudication: its two flagship claims were checked against the actual module and upheld — C1 (parity matrix maps to methods LogicBoxes doesn't override) and C2 (forwarding/DNSSEC shipped today but deferred) are factually correct, and are carried above as High findings (down-calibrated from the reviewer's Critical because the FR substance survives and every fix is self-contained). Its async/idempotency criticals (C3/C4/H3) are upheld at the WHAT-level and carried under Done-ness; the reviewer over-escalated the “mechanism not specified” angle, since a PRD may defer mechanism to architecture. The findings below were verified or partially upheld but not promoted to top-level; the adversarial voice is preserved. Full detail in the source file.

medium

C5 — EPP/auth-code parity is mis-claimed; the feature flag is wrong relative to the baseline

§6; FR33; §9
config.json does not enable epp_code, so LogicBoxes' supportsEppCode() is the abstract default (false) and it surfaces the auth code via the Settings tab (manageSettings), not sendEppEmail/updateEppCode. So §6's EPP rows are net-new, not parity — a specific instance of the C1 framing problem. (Security half of this is carried as the Medium auth-code-redaction finding under Done-ness.)
Fix: Reclassify EPP send/reset as “net-new, exceeds baseline”; keep the Settings-tab read of the current auth code as the true LogicBoxes-equivalent.
medium

H1 — Pricing currency model ignores Blesta's conversion path

FR7/FR8; §4.4; OQ3
LogicBoxes' getFilteredTldPricing uses $this->Currencies->convert(...) to convert registrar cost into the operator's configured currencies; FR7's “USD plus any local currency WebNIC returns” ignores that operators price in their currencies, which may be neither. This surfaces as empty TLD pricing for any operator whose currency WebNIC doesn't return.
Fix: Require the module to support Blesta's currency-conversion path (mirroring Currencies->convert); resolve OQ3 before freezing FR7.
medium

M2 — Token-refresh “stampede” clause contradicts NFR1's “cache only”

FR5; NFR1; NFR6
Preventing a refresh stampede across concurrent PHP-FPM/cron workers needs shared, lockable state, but NFR1 says tokens live “in memory/cache only, never persisted.” In a classic deployment there is no shared in-process memory, and the cache backend/locking is never defined — so FR5 is unimplementable as written.
Fix: Specify the token cache backend and single-flight/locking strategy and reconcile with NFR1, or downgrade the no-stampede clause to best-effort-per-process.
medium

M6 — Multi-step registration saga has no partial-failure / orphan-cleanup spec

FR14–FR16
Registration is now a saga (contacts → registrant account → hosts → register). If hosts are created then register fails, you accumulate orphaned WebNIC objects — the very orphans §4.3 warns about — with no compensation spec.
Fix: Add an orchestration-failure FR: deterministic lookup-before-create so retries reuse, and a defined stance on orphans (reuse-on-retry over delete-on-failure). Tie to the idempotency FR.
low

H4/H6/M3/M5/L1–L5 — further verified-or-plausible items

see review-adversarial-general.md
Includes: “basic vs full DNS” boundary undefined (FR35); suspend/cancel semantics unverified against the baseline (FR25/FR26 — cancelService at logicboxes.php:596 should be read); auto-renew conflict risk with Blesta automation (OQ2/FR23/FR40); OTE-vs-production catalogue divergence (§12); cron-ownership fork left open (§9/FR39); dynamic rule endpoints lacking fallback (FR19/FR24).
Fix: Triage these during the Update pass; most are “confirm against the checkout / OTE” or single-sentence clarifications.

Mechanical notes

  • Adjudication of the reviewer conflict. The rubric walker certified §6 as “verifiably accurate against the actual RegistrarModule contract and shipped logicboxes module.” That holds for the abstract contract and the config.json feature flags only. Direct inspection of components/modules/logicboxes/logicboxes.php (getClientServiceTabs ~line 1273, addService line 185, and the absence of any cron() method) is the basis for the two High parity findings (C1, C2) and the async finding (C3).
  • Dual FR/section numbering. FRs are flat (FR1…FR59) while parent sections are decimal (§7.1–§7.3). Harmless but mixed; no gaps or duplicates in FR1–FR59 or NFR1–NFR14. Downstream extractors should key on the flat FR IDs.
  • Two overlapping “out of scope” sections (§1.3 and §10) plus §2.3 Non-goals — content is consistent across all three but the duplication invites drift; consider one canonical Non-Goals section with the others cross-referencing it.
  • §6 endpoint names are descriptive labels, not literal API paths (e.g. “Query Domain,” “Register Domain”) except where a path is given. OQ1 already flags that exact schemas need OTE confirmation — architecture should not treat the label column as canonical endpoint identifiers.
  • Cross-references resolve. “see parity matrix §6,” “Section 2/3,” and the §9↔§6 mapping all point to real targets; the apidoc.webnic.dev/llms.txt source and components/modules/logicboxes/ baseline both exist in this checkout.
