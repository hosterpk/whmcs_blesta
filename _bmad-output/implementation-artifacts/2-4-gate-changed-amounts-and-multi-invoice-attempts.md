# Story 2.4: Gate Changed Amounts and Multi-Invoice Attempts

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a customer paying through KuickPay,
I want the gateway to block ambiguous payment attempts,
so that the reference I pay cannot be misapplied to the wrong invoice amount.

## Acceptance Criteria

1. **AC1 — Amount / mapping change follows configured policy.** Given a Pending Voucher exists, when the invoice amount or invoice mapping has changed, then the system follows the configured replacement or blocking policy and it does not silently reuse a stale amount.
2. **AC2 — Discount makes the stale reference non-payable.** Given a customer has a Pending Voucher and staff applies a discount to the invoice, when the customer returns to the KuickPay payment page, then the gateway detects that the stored Voucher amount no longer matches the invoice payable amount and the stale Consumer Number is not shown as payable for the discounted invoice.
3. **AC3 — Replacement policy retires and re-issues.** Given the configured policy allows replacement after an invoice discount, when the customer requests KuickPay payment for the updated invoice, then the old local Voucher is retired from active reuse while preserving audit history and a new Voucher is created or issued for the updated payable amount.
4. **AC4 — Multi-invoice attempt blocked when not enabled.** Given a customer attempts to pay multiple invoices, when deterministic invoice amount allocation is not implemented or not enabled, then the gateway blocks the attempt with localized customer copy and no Voucher is created.
5. **AC5 — Multi-invoice deterministic storage when enabled.** Given multi-invoice support is enabled in a later policy, when the attempt is accepted, then each invoice ID and amount allocation is stored deterministically.

> **All five ACs must hold without breaking Story 2.1/2.2 create-or-reuse, Story 2.3 issuance + sequential-reload safety, Story 1.5 PKR eligibility, or Story 1.1 companion guards.** The single-invoice happy path (create → issue → display, and a matching reload displaying the already-issued voucher) must remain unchanged. This story **adds gates around** that path; it does not rewrite it.

- [x] **Task 7 — Deterministic multi-invoice storage when `allow` (AC5)**
  - [x] When `multi_invoice_policy === 'allow'` and the attempt is multi-invoice, the create path must store the allocation **deterministically**:
    - **Dedupe invoice IDs — fail closed, do NOT last-wins/sum.** Before building `$invoiceLinks` (`KuickPayVoucherReferenceService.php:102-108`), a repeated ID violates the `(voucher_id, invoice_id)` unique key (`kuickpay_reconcile_plugin.php:82`) and rolls back the whole create (the 2.1 duplicate-id deferral). If two rows carry the **same** invoice ID, **reject/fail-closed** (set `lastError`, return `null`) — do **not** implement last-wins or sum (both silently drop or distort per-invoice amount data). An identical-duplicate (same ID, same amount) may be collapsed to one link; any same-ID/different-amount is a fail-closed reject.
    - Store **each invoice's own amount** in its link row (already supported by the loop; ensure it uses `invoice_amount['amount']`, not the voucher total).
    - **Do NOT add a `sum(invoice_amounts) === total` allocation check.** It would **false-block legitimate payments**: Blesta passes `$amount = account_credit + sum(invoice_amounts)` (`client_pay.php:897,907` — `$total` seeds from `$payment['credit']` then adds each invoice), and the credit breakdown is **not visible inside `buildProcess()`** (only `$amount` + `$invoice_amounts` arrive). So `sum(invoice_amounts)` legitimately differs from `$amount` whenever the customer adds credit, and the gateway cannot distinguish that from a corrupt allocation. AC5 integrity is satisfied by per-invoice link storage + dedupe, not by a sum check. (If a real allocation-integrity check is ever wanted, it requires extending the gateway's `buildProcess()` contract to receive credit context — a separate story, not 2.4.)
    - **Canonical reference + reuse keying:** generate the reference and perform the reuse lookup keyed on the **sorted distinct invoice-ID set**, not `invoice_amounts[0]` alone, so the same multi-invoice set deterministically reuses/maps the same voucher across reloads (closes the 2.1 reuse-by-first-invoice deferral for the `allow` case).
    - **Keying contract — do NOT touch the visible reference vocabulary.** Single-invoice references keep the existing `{invoice_id}` behavior **unchanged**. The set-based identity is an **internal** company-scoped key (the `context_key` concept from Task 9, or an in-service derivation if Task 9 is deferred) used for the reuse *lookup* and the `(voucher_id, invoice_id)` link rows — **not** a new reference-pattern token. Do **not** add a token to `expandPattern()` (its vocabulary is `random_prefix`/`invoice_id`/`institution_id`/`registration_number`, `KuickPayVoucherReferenceService.php:217`) or change `generateReferences()`'s `{invoice_id}` derivation for the single-invoice path — legacy reference patterns must remain byte-for-byte stable.
    - **Set-lookup is REQUIRED (not optional) when Task 9 is deferred, and carries a concurrency residual.** If Task 9 ships, reuse keys on the `context_key` column (`WHERE context_key = ? AND status = 'pending'`). If Task 9 is **deferred**, AC5 reuse still needs an application-level set lookup: add `getPendingByInvoiceSet(array $invoiceIds, int $companyId): ?stdClass` to the repository (match a `pending` voucher whose linked-invoice set equals the sorted distinct set exactly) — this is **required for the `allow` path**, not optional. Note the limitation: **without Task 9's `active_context_key` unique key, two concurrent multi-invoice creates for the same set can both miss the lookup and both insert** — the same double-submit residual as single-invoice (deferred-work.md:72), now extended to multi-invoice. State it explicitly rather than implying set-keying alone closes concurrency.

Implement AC4 (block) as the firm behavior and AC5's deterministic **storage** so enabling `allow` is safe and tested. The broader multi-invoice **customer display** (per-invoice breakdown) stays minimal — the single Consumer Number covers the combined total — and is out of 2.4 scope.

### How the change is actually detected (grounded in the Blesta pay flow)
`buildProcess(array $contact_info, $amount, array $invoice_amounts = null, array $options = null)` (the `= null` defaults are part of the real signature; `(array) $invoice_amounts` re-wraps at `kuickpay.php:591`) is called **fresh on every render** of the client confirm page (`app/controllers/client_pay.php::confirm()` → `Payments::getBuildProcess()` → `GatewayPayments::getBuildProcess()` → `buildProcess()`). `$invoice_amounts` arrives as `[ ['id'=>invoice_id, 'amount'=>amt], ... ]` (built in `Payments::getBuildProcess()` from the per-invoice apply-amounts), and `$amount` is the total.

- The **current requested amount/mapping** = the incoming `$context` (`buildVoucherReferenceContext()` normalizes both, `kuickpay.php:679-680`). The **stored** amount = the voucher row / its links.
- **Change = stored ≠ incoming** (normalized). This is the detection signal — no need to re-query the Invoices model for the default path.
- **Session-cache caveat (important):** the apply-amounts are written to the client **session** when the customer selects invoices in `client_pay::index()`/`method()`, and `confirm()` reads them from session (not a fresh DB read). So when the customer **returns to the payment page** (re-enters the pay flow, the AC2 wording), `index()`/`method()` reload the invoice and refresh the session → the incoming `$amount` reflects the **new** (discounted) balance → mismatch is detected. A pure browser **refresh** of `confirm` reuses the stale session amount, so detection may not fire on that narrow path. This is acceptable for MVP: it fails **safe** (shows the old amount the customer already agreed to; reconciliation/posting validation in Story 3.4 is the ultimate backstop — a true mismatch routes to Manual Review, never mispays). **Optional hardening (not required):** additionally re-query the invoice's live balance via the `Invoices` model and compare — adds coupling; document the trade-off if you do it. Recommended primary = incoming-amount comparison. [Explore: client_pay.php confirm/index/method; payments.php getBuildProcess]

### Replacement design detail (AC3) — and its real-world safety boundary
- Retire = `edit($id, $company_id, ['status' => 'cancelled'])` (keep the row + references) → audit `voucher.replaced` → create + issue a new voucher for the current amount. The reload matrix already treats `cancelled` as ALLOW (`kuickpay.php:793`), so a subsequent reload regenerates cleanly (FR23).
- **Two-live-references caveat (OPEN DECISION B):** if the retired voucher was already issued at KuickPay, the provider reference stays live (no MVP cancel API). A customer who pays the **old** reference is caught by **Bulk Reconciliation (3.7)** matching on the stored Consumer Number → Manual Review, never auto-posted (single-inquiry `getReconcilable` only picks `pending`/`retry`, `kuickpay_vouchers.php:227`; posting validation 3.4 re-checks amount/state). `replace` is **code-gated out of production** until that net lands (Task 1 / OPEN DECISION B), so `block` is the only reachable production behavior and this state cannot occur in production yet.
- **Safety-net is not yet built — `replace`/`allow` are CODE-GATED out of production (not just default-off).** The operational backstops that make a late payment on a retired-but-issued reference safe — posting validation (3.4, `ready-for-dev`), safe posting (3.5, `backlog`), and the bulk-reconciliation net (3.7, `backlog`) — are **not delivered as of this story** (`sprint-status.yaml`). A retired-but-issued reference paid by the customer is **not** caught by current single-inquiry reconciliation (`getReconcilable` is `pending`/`retry` only — `cancelled` is excluded, `kuickpay_vouchers.php:227`), and no posting service exists yet. So per the resolved decision, the `replace`/`allow` paths are **implemented and unit-tested but not production-selectable**: the settings option lists and `editSettings()` validation accept **`block` only** (Task 1), `// TODO(3.7)`. This is a **code-enforced gate**, not operator discipline — production cannot reach the two-live-references state. When 3.4/3.5/3.7 land, un-gating is a one-line widen of the option list + validation enum (the labels and paths already exist).
