# Story 3.6: Handle Expiry, Late, Partial, and Overpayment Cases

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a finance operator,
I want policy-sensitive payment exceptions handled explicitly,
so that unsafe payment states do not silently mark invoices paid.

## Acceptance Criteria

> Epic source (BDD, [Source: _bmad-output/planning-artifacts/epics.md#Story-3.6 lines 671-687]):
> - **Given** a Voucher passes its configured expiry date unpaid **When** expiry processing runs **Then** it transitions out of active Pending state **And** the customer can generate a new Voucher if the invoice remains unpaid.
> - **Given** payment evidence is underpaid, overpaid, late after expiry, or policy-dependent **When** validation runs **Then** configured policy is applied **And** unsupported or unsafe cases go to Manual Review without full invoice payment.

This story closes **FR21** (under/over/late policy) and **FR23** (local voucher expiry), and is the policy layer that Stories 3-4 and 3-5 deliberately deferred ([Source: 3-5 story AC10 — "Underpayment, overpayment, late-after-expiry, and partial cases are out of scope here (Story 3.6) and must never be force-posted by this service"]; [Source: deferred-work.md 3-4 items]).

The following testable criteria expand the two BDD scenarios. Each maps to tasks below.

### Part A — Local voucher expiry (FR23)

1. **AC1 — Expirable selector.** A new bounded selector `KuickpayVouchers::getExpirable(int $company_id, int $limit, int $after_id = 0): array` returns vouchers where `company_id = ? AND currency = 'PKR' AND status IN ('pending','retry') AND date_expires IS NOT NULL AND date_expires < CURDATE()`, ordered by `id ASC`, limited to `$limit`, with `id > $after_id` resume support — mirroring the existing `getPostable()`/`getReconcilable()` shape **including their `currency = 'PKR'` guard** (`getPostable` filters PKR at kuickpay_vouchers.php:371; `getReconcilable` at :324). The PKR guard keeps the sweep from ever expiring a malformed or future non-PKR row. A `KuickPayVoucherRepository::getExpirable(...)` passthrough is added (mirror the existing `getPostable` passthrough, KuickPayVoucherRepository.php:223-226). [Source: plugins/kuickpay_reconcile/models/kuickpay_vouchers.php:366-379; FR23 (epics.md:69)]

2. **AC2 — Expiry sweep transitions out of active Pending.** A new method `KuickPayReconcileService::expirePending(int $company_id): array` fetches up to `BATCH_SIZE` expirable vouchers via `getExpirable()`, and for each transitions `status` to `'expired'` via the **company-scoped** `voucherRepository->edit((int) $voucher->id, $company_id, ['status' => 'expired'])` (the model `edit()` already drops `company_id` and stamps `date_updated`, kuickpay_vouchers.php:83-98). It is bounded by `BATCH_SIZE` and the existing `MAX_RUNTIME_SECONDS` guard, advances by `id`, and is **idempotent on rerun** (a now-`expired` row no longer matches `getExpirable()`). Returns `['status' => 'completed'|'skipped'|'aborted', 'counts' => ['processed','expired','errors']]`. [Source: epics.md:679-682 "transitions out of active Pending state"; KuickPayReconcileService.php:50-120 run-loop shape]

3. **AC3 — Expiry preserves audit history.** Each transition writes a `voucher.expired` audit event via `KuickPayAuditService::record('voucher.expired', [...])` with a **redacted** payload only (`company_id`, `voucher_id`, `payload => ['prior_status' => <pending|retry>]`; no secrets, no PII, no raw SOAP). No voucher row is deleted; all evidence/diagnostic/date fields are preserved. [Source: architecture.md:614-634 audit requirements; FR23 "preserving audit history"; NFR4]

4. **AC4 — Bounded, locked, scheduled trigger.** A dedicated plugin cron task `expire_vouchers` drives the sweep with a **distinct DB lock** name (`expire_vouchers`) via the existing `KuickPayReconcileLockRepository`, registered idempotently through the plugin install/upgrade path (plugin version bump `1.2.0 → 1.3.0`, a new cumulative `version_compare(... '1.3.0', '<')` upgrade gate calling the idempotent `addCronTasks()`, plus a `getCronTasks()` entry and `cron($key)` dispatch). Expiry is a **local DB lifecycle sweep that performs no SOAP call**, so — unlike reconcile — it is **NOT gated by `reconciliation_enabled`**. Use an interval ≥ the reconcile cadence (e.g. 60 minutes; `date_expires` is date-granular so frequent runs are unnecessary and the sweep is idempotent). [Source: architecture.md:451-458 cron requirements; architecture.md:661 "Cron posting without row locks" anti-pattern; 3-5 story Task 5 cron-registration pattern]

5. **AC5 — Customer can generate a new Voucher if the invoice remains unpaid.** Once a voucher is `expired`, the gateway's existing `reloadVoucherDecision()` already returns `'allow'` for an `expired` latest voucher (kuickpay.php:869-870), so `buildProcess()` creates/issues a **fresh** voucher for the still-unpaid invoice via `createVoucherForContext()` (kuickpay.php:673-680). This AC **verifies and regression-tests** that path (no new gateway branch is required for the allow decision); the new voucher gets a new Registration/Consumer Number and a new payable reference. Blesta only routes the gateway for unpaid invoices, so the "remains unpaid" precondition is inherent to the pay flow. [Source: components/gateways/nonmerchant/kuickpay/kuickpay.php:852-874 reloadVoucherDecision; architecture.md:604 `expired` row "generate/pay again if flow allows"]

6. **AC6 — Expiry never corrupts invoice/payment state.** The sweep mutates **only** `kuickpay_vouchers.status` (+ `date_updated`); it creates/applies **no** Blesta transaction, touches **no** invoice or `transactions` row, and calls **no** `KuickPayPostingService`. The selector excludes `confirmed_unposted`/`posted`/`failed`/`manual_review`/`cancelled` vouchers, so validated evidence and posted payments are never expired. [Source: NFR2 (epics.md:89); architecture.md:652 posting-only-class anti-pattern]

### Part B — Underpayment / overpayment / late-after-expiry policy (FR21)

7. **AC7 — Amount-direction classification (in the parser, where it is reachable).** Directional under/over classification belongs to `KuickPayResponseParser`, **not** the validator. On the live single-inquiry reconcile path the parser compares the paid amount (`fields[3]`) against the voucher amount it receives as `expected_amount`, and on disagreement already sets `error_class = 'amount_mismatch'` and routes the evidence to `manual_review` **before** it can become `confirmed_unposted` (KuickPayResponseParser.php:466-502; context fed by `buildParserContext()`, KuickPayReconcileService.php:172-179). Because the validator runs **only** for `confirmed_unposted` evidence (`persistEvidence()` gate, KuickPayReconcileService.php:199), a directional check added to the validator would be **dead code** for both live paths (reconcile evidence is exact by the time it reaches the validator; posting evidence is reconstructed equal). So extend the **parser's** amount-mismatch branch to classify by direction: paid `<` expected ⇒ reason `underpayment`; paid `>` expected ⇒ reason `overpayment` (only when both normalized amounts are present and unequal; an unparseable/missing amount keeps existing fail-closed behavior). Keep the `error_class` column unchanged at `ERROR_AMOUNT` (`'amount_mismatch'`, an existing enum value) — refine only the machine reason code carried in the evidence `validationErrors` array. Reason codes are **bare machine codes only** (no interpolated amounts/identifiers/PII). The validator's own `amountMatches()` is left as-is — it still emits generic `amount_mismatch` for the validator-only "voucher amount ≠ sum(invoice-link allocations)" mapping inconsistency, a different concern and the case the existing validator test exercises. An **exact** amount still passes. [Source: KuickPayResponseParser.php:466-502; KuickPayReconcileService.php:172-179,199; FR21 (epics.md:65); NFR13 no-float (epics.md:111)]

8. **AC8 — Late-after-expiry detection (validator fence).** The late check lives in `KuickPayEvidenceValidator` as the fail-closed fence for **confirmed** evidence: it emits reason `late_payment` when the Voucher has a non-empty `date_expires` **and** the evidence paid date (`KuickPayEvidence::paidAt()`, `Y-m-d`, at `components/gateways/nonmerchant/kuickpay/lib/KuickPayEvidence.php:107-110`) is strictly **after** `date_expires`. When `date_expires` is null/empty **or** `paidAt()` is null, the check is a **no-op** (emits nothing), keeping existing 3-4/3-5 evidence (null/future `date_expires`) unaffected. Date comparison uses string/`DateTime` comparison of `Y-m-d` values, never floats. **Reachability honesty:** on the live *single-inquiry reconcile* path this check is effectively **defense-in-depth** — `getReconcilable()` excludes a non-null past-expiry voucher from inquiry (`date_expires >= today`, kuickpay_vouchers.php:328) and Part A's sweep transitions it to `expired` instead, while a null `date_expires` makes the check a no-op. It becomes **materially reachable for the 3-7 bulk path**, where a different selector can surface confirmed paid evidence whose `paidAt()` post-dates `date_expires`. Putting the fence in the single shared validator now means bulk inherits it for free. [Source: KuickPayEvidence.php:107-110 paidAt; kuickpay_vouchers.php:34 date_expires, :328 reconcile expiry exclusion; architecture.md:49 "late ... must fail closed"; NFR9]

9. **AC9 — Configured policy surface ("configured policy is applied").** Three gateway enum settings are added — `underpayment_policy`, `overpayment_policy`, `late_payment_policy` — each defaulting to and validated as the **single safe value `manual_review`**. Mirror the *structure* of the `amount_change_policy`/`multi_invoice_policy` block-only enum pattern (kuickpay.php:159-164, 278-293) and add the three to the `paymentPolicyOptions()` helper (kuickpay.php:115-129), **but substitute `manual_review` everywhere the mirrored block uses `block`** (default, `in_array` allow-list, `getSettings()` `??` fallback, `settings.pdt` select default) — do not copy the `block` value through. Tag the widen point `// TODO(production-gate): widen ...` (this is the *intended new* tag; the existing siblings use `TODO(3.7)`, so do not search for `TODO(production-gate)` in the current gateway — it is not there yet). The three keys are threaded into `KuickPayReconcileService::gatewayConfigForCompany()` (return array ~:336-346; the existing `amount_change_policy`/`multi_invoice_policy` are deliberately **not** in this array — they are consumed at voucher-creation time, whereas these three are the first settings consumed at reconcile time). A classified exception reason can arrive **two ways**: `underpayment`/`overpayment` as **parser-level `manual_review`** evidence (already carried in `diagnostic_summary.validation_errors` via `diagnosticSummary()`, KuickPayReconcileService.php:256-266) and `late_payment` via the **validator-invalid** branch. In both cases the service **reads the configured policy** for the present reason and resolves the target status via `resolveExceptionStatus()` (the resolved gateway config must first be made reachable inside `persistEvidence()` — it is **not** threaded there today; see Task 6); in MVP every supported policy value resolves to `manual_review`. The classified reason is merged into `diagnostic_summary.validation_errors` (reuse `mergeValidationErrors()`, KuickPayReconcileService.php:268-277) and surfaced via the existing `evidence.rejected` audit. [Source: FR21 "applies configured business rules"; architecture.md:96,320-325,974-975 deferred policy decisions; epics.md Additional-Requirements "Open production-gate decisions remain for partial payments, overpayments, late payments"]

10. **AC10 — Fail closed: no full invoice payment.** Underpaid, overpaid, and late-after-expiry evidence never transitions a Voucher to `confirmed_unposted` or `posted`, creates **no** Blesta transaction, and marks **no** invoice paid. All such cases route to `manual_review` carrying their classified reason. There is no "force paid" path and no partial/over crediting in MVP. [Source: NFR9 (epics.md:103); architecture.md:49,660 anti-patterns; epics.md:684-687]

11. **AC11 — Controlled regressions across the validation paths.** The **validator** change is **purely additive** (the new `late_payment` no-op-when-absent check), so all existing `KuickPayEvidenceValidatorTest` and `KuickPayPostingServiceTest` cases MUST pass **unchanged** (the existing validator `amount_mismatch` test is the link-sum case — evidence equals voucher — and is untouched). The **parser** change (directional under/over) intentionally **updates** the reason-code expectations of the parser-level amount-mismatch tests and the matching reconcile fixture mapping — these are deliberate, enumerated test updates, **not** silent regressions: `error_class` stays `amount_mismatch` (so `KuickPayReconcileServiceTest::fixtureMappingProvider`'s `error_class` assertion is unaffected) while the `validationErrors` reason becomes `underpayment`/`overpayment`. The late check defaults to no-op when data is absent (null `date_expires` or null `paidAt()`), and reconstructed posting-time evidence has `evidenceAmount === voucherAmount` by construction so nothing new fires at posting. Keep the validator's `array $allowedStatuses = ['pending','retry']` default (posting passes `['confirmed_unposted']`). [Source: 3-5 story AC14; KuickPayEvidenceValidator.php:25-30; KuickPayResponseParserTest.php:164-170; KuickPayReconcileServiceTest.php:112-118]

12. **AC12 — Amount/date math safety.** All amount comparisons use the existing integer-minor-unit helper `toMinorUnitsOrNull()` (never PHP floats); date comparisons use `Y-m-d` string/`DateTime` comparison. [Source: NFR13 (epics.md:111); architecture.md:593,658]

13. **AC13 — Honest, fixture-backed verification.** New/updated tests cover: the `getExpirable` selector (incl. **non-PKR and not-yet-expired rows untouched**); `expirePending()` transition + `voucher.expired` audit + idempotent rerun; the gateway `expired`→`allow`→new-voucher regeneration path; **parser** under/over classification (the existing `bill-payment-inquiry-amount-mismatch.xml` — paid `900.00` vs voucher `1000.00` — now classifies as `underpayment`; add an overpayment fixture) with `error_class` still `amount_mismatch`; **validator** `late_payment` classification (and exact still passes, link-sum mismatch still `amount_mismatch`); reconcile-path under/over/late evidence ⇒ `manual_review` + classified reason in `diagnostic_summary` + `evidence.rejected` audit + no posting fields + configured policy read; and the gateway `testPaymentPolicySettingsAreProductionGatedToBlock()` updated to the new five-key option array. Reuse existing fixtures and add single-inquiry overpayment + late-after-expiry fixtures (see Task 8). Run with the external PHPUnit 8.5 runner; `php -l` every changed file; do not claim root PHPUnit coverage unless sibling `../tests` exists. [Source: project-context.md Testing Rules:69-81; FR28 (epics.md:79)]

## Dev Notes

### What this story is (and is NOT)

This is the **policy + expiry** layer. It does **two** things:
1. **FR23 — local voucher expiry:** transition unpaid `pending`/`retry` vouchers past their `date_expires` to `expired`, on a schedule, so they leave the active set and the customer can get a fresh reference.
2. **FR21 — under/over/late policy:** classify payment amount/date exceptions explicitly — `underpayment`/`overpayment` at **parse time** (where they are reachable and fail closed) and `late_payment` at **validation time** — and route them through a **configured policy** whose only MVP-safe value is `manual_review` — never full payment.

**NOT in scope:** posting (3-5 owns it; never call `KuickPayPostingService` here), bulk reconciliation (3-7), the admin Manual Review queue/detail views and run-summary UI (Epic 4 / Story 4.4), a "force paid" action (forbidden in MVP), any actual *acceptance* of partial/over/late as payment (a deferred production-gate decision — architecture.md:96,320-325,974). Do not create `KuickPayVoucherStates`/`KuickPaySchema`/`KuickPayVoucherNormalizer` (architecture lists them but they are not built and not this story).

### The expiry gap this story closes (read this first)

`KuickpayVouchers::getReconcilable()` (kuickpay_vouchers.php:313-356) **already excludes** vouchers past `date_expires`:
```php
->open()
    ->where('date_expires', '>=', date('Y-m-d'))
    ->orWhere('date_expires', '=', null)
->close()
```
So a `pending` voucher whose `date_expires` has passed is **silently dropped from reconciliation but never transitioned** — it sits as `pending` forever, invisible. That is the FR23 gap. There is **no** existing local expiry sweep. (The parser's `02`→`expired` mapping in `mappedStatus()`, KuickPayReconcileService.php:249-250, only fires for vouchers that ARE inquired — and past-expiry vouchers are excluded from inquiry — so the parser path does **not** cover local time-based expiry.) Your `expirePending()` sweep is the missing piece.

`date_expires` is set at voucher creation from the `expiry_date_offset_days` gateway setting via `KuickPayVoucherReferenceService::offsetDate()` (`date('Y-m-d', strtotime('+N days'))`) — no change needed there.

### Customer regeneration already works once the row is `expired`

`reloadVoucherDecision()` (kuickpay.php:852-874) returns:
- `'pending'` + empty reference → `'issue'`; `'pending'` + reference → `'display'`
- `'failed'` + `credential_error` → `'allow'`
- `'expired'` **or** `'cancelled'` → `'allow'` (line 869-870) → `buildProcess()` creates a **new** voucher
- anything else → `'block'`

So the FR23 "customer can generate a new Voucher" half is **already implemented** — it was just unreachable because nothing set `expired`. Your sweep makes it reachable. AC5 is mostly a verification + regression test, not new gateway logic.

### Where each exception is classified — parser vs validator (FR21)

There are **two** validation surfaces on the live path, and the new reasons split across them by **reachability**:

- **`KuickPayResponseParser` owns evidence-vs-expected field checks** (amount direction, currency, reference). It compares the paid amount against the voucher amount it receives as `expected_amount` and **fails closed to `manual_review` before evidence can become `confirmed_unposted`** (KuickPayResponseParser.php:466-502). This is the **only** place a single-inquiry under/overpayment is reachable, so directional `underpayment`/`overpayment` classification lives here. ⚠️ A directional check added to `KuickPayEvidenceValidator` would be **dead code**: the validator runs only for `confirmed_unposted` evidence (`persistEvidence()` :199), and by then the parser has guaranteed the amount is exact. Relaxing the parser to let an amount-mismatched evidence through to `confirmed_unposted` is **forbidden** — the posting cron (`getPostable`) would pick it up and post it (fail-open). So the parser keeps routing the mismatch to `manual_review`, and that is also where the direction is refined.
- **`KuickPayEvidenceValidator` owns invoice-link consistency and temporal checks on confirmed evidence.** It keeps the generic `amount_mismatch` for the validator-only "voucher amount ≠ sum(invoice-link allocations)" mapping inconsistency (the case its existing test exercises), and it gains the **`late_payment`** check — reachable here because an exact-amount-but-late payment passes the parser and arrives as `confirmed_unposted`.

Both surfaces keep the **routing identical** (all → `manual_review`, never full payment). The reconcile service then reads the configured policy for whichever classified reason is present — parser-level under/over **or** validator-level late (see "Configured-policy surface" below). This division already matches how the code is structured (parser checks amount/currency/reference; validator checks link-sum + freshness); this story refines the parser's reason code and adds the validator's late check.

**Reason-code policy (matches 3-4's design):** the codes `underpayment`, `overpayment`, `late_payment` are **bare machine codes** carried only in `diagnostic_summary.validation_errors` (and the redacted audit payload), never interpolated with amounts/identifiers. They are **not** written to the top-level `error_class` column: for under/over the parser keeps `error_class = 'amount_mismatch'` (an existing enum value), and `late_payment` sets no `error_class`. The architecture's 8-value `error_class` enum is fixed; adding values is a documented architecture change (architecture.md:646) — out of scope. [Source: 3-4 story Dev Notes "Outcome → state / audit / error_class mapping"]

### ⚠️ Why the new checks can't break posting (3-5) (AC11)

Posting (3-5) does **not** re-parse — it reconstructs `KuickPayEvidence` from stored voucher fields (`amount = $voucher->amount`, etc. — see 3-5 Task 3 step 5) and calls the validator with `['confirmed_unposted']`. So the **parser's** new directional under/over never runs at posting at all, and the reconstructed `evidenceAmount === voucherAmount` by construction. The validator's only new check, **`late_payment`**, could in principle fire at posting if a `confirmed_unposted` voucher had `paid_at > date_expires` — but on the single-inquiry path such a voucher never reaches `confirmed_unposted` (a non-null past-expiry voucher is excluded from `getReconcilable` and swept to `expired` by Part A instead; see AC8 reachability note), and existing 3-5 fixtures use null/future `date_expires`. **Guard:** the late check is a strict no-op when `date_expires` is empty or `paidAt()` is null, so no existing 3-4/3-5/posting test regresses. The validator change is therefore purely additive; the parser change updates only the parser's own amount-mismatch tests + the matching reconcile fixture expectation (`error_class` unchanged). Run the full plugin **and** gateway suites to confirm.

### Configured-policy surface — minimal but real (AC9)

FR21 says the system "applies configured business rules." The architecture defers the *actual* under/over/late acceptance behavior to a production gate (architecture.md:96,320-325,974). The MVP-correct resolution: add the **config surface** (`underpayment_policy`/`overpayment_policy`/`late_payment_policy`) with a single safe value `manual_review`, like `amount_change_policy`/`multi_invoice_policy` ship today (block-only enum + `TODO` to widen, kuickpay.php:278-293) — but with `manual_review` substituted for `block` (see Task 6 footgun note). The reconcile service **reads** the policy and resolves it (MVP: always `manual_review`). This literally satisfies "configured policy is applied," keeps fail-closed, and makes the future production decision a settings/enum change rather than a code rewrite. Do not over-build a policy engine — a tiny resolver returning `manual_review` is correct for MVP.

**Two arrival paths into the resolver.** `late_payment` reaches `persistEvidence()` via the validator-invalid branch (the evidence was `confirmed_unposted`). `underpayment`/`overpayment` reach it as **parser-level `manual_review`** evidence that **skips the validator block** (the `isConfirmedUnposted()` gate at :199 is false). So `resolveExceptionStatus()` must read the configured policy off the **final merged `validation_errors`** — not only inside the validator branch — or the parser-classified under/over would never have its policy "applied." In MVP both still resolve to `manual_review`, so the outcome is unchanged; the value added is the directional reason code + a single real extension point for the production gate.

**Plumbing caveat (verified):** the resolved gateway config is **not in scope** inside `persistEvidence()` today — `run()` keeps it in a local and `$this->gatewayConfig` is `null` in production — so Task 6 first makes it reachable (set `$this->gatewayConfig = $gateway_config` after the `run()` null-guard, then read it). And because `resolveExceptionStatus` runs on the merged reasons at a single post-block site, it **must return the current status unchanged when no under/over/late reason is present**, or it would downgrade a valid `confirmed_unposted` voucher to `manual_review`.

### Transaction boundary / locking for the expiry sweep

The expiry sweep is a sequence of independent single-row `UPDATE`s (status→expired) + audit writes; it does **not** need a `FOR UPDATE` row lock or a wrapping DB transaction (it is not posting money). The **DB-backed cron lock** (`expire_vouchers` via `KuickPayReconcileLockRepository`) is what prevents two cron workers from double-sweeping; the per-row UPDATE is naturally idempotent (a now-`expired` row no longer matches `getExpirable()`). This mirrors the reconcile run's lock usage (KuickPayReconcileService.php:57-117), not the posting service's `FOR UPDATE` discipline. Always release the lock in a `finally`.

The sweep touches **only** the voucher row's `status` (+`date_updated`); it does **not** delete or modify `kuickpay_voucher_invoices` link rows — they persist alongside the `expired` voucher for audit and regeneration reference. **Clock note:** `getExpirable` compares against the **DB** clock (`CURDATE()`) while the existing `getReconcilable` excludes past-expiry rows using the **PHP** host clock (`date('Y-m-d')`, kuickpay_vouchers.php:328). Under host/DB drift a voucher can be dropped from reconcile (PHP says expired) a few hours before the sweep selects it (DB says not-yet) — a bounded ≤1-day limbo that self-heals on the next idempotent run. Aligning `getReconcilable` to a DB-side date comparison is a clean follow-up, out of scope here.
