## Captured Product Intent

- The gateway is not a new standalone product experience. It extends Blesta with a local Pakistan KuickPay bill/reference payment path.
- Customer experience centers on generating or reusing a payable Voucher, showing the Consumer Number, amount, due date, expiry date, and payment instructions, then setting expectations that Blesta updates only after confirmation.
- Staff experience centers on searchable Voucher visibility, normalized status, sanitized diagnostics, safe manual checks, Manual Review, and reconciliation run summaries.
- Payment truth must fail closed. Unknown, mismatched, duplicate, late, or unmatched payment evidence must not become a paid invoice state.

## UX Decisions

1. Inherit Blesta UI conventions instead of defining a separate visual identity.
   - Evidence: existing client/admin surfaces use Bootstrap-style `card`, `alert`, `btn-*`, `badge`, table, form, `Widget`/`WidgetClient`, Bootstrap Icons, and Font Awesome patterns.
   - Consequence: `DESIGN.md` defines only KuickPay-specific token aliases and component deltas.

2. Treat the Customer Payment Reference page as the primary customer-facing surface.
   - It must keep the Consumer Number visible without expanding instructions.
   - It must make copy behavior explicit and confirm that generating a Voucher does not mean payment has been received.

3. Treat the admin Voucher list and Voucher detail as operational control surfaces.
   - Support and finance need search, filters, clear status, last inquiry, transaction linkage, raw diagnostic summary, and safe manual actions.

4. Keep raw diagnostic material admin-only and sanitized.
   - Diagnostics support troubleshooting but must not be exposed to customers or include credentials.

5. Use Manual Review as an explicit UX state, not only a backend flag.
   - Staff need reason, evidence, notes, and next actions for ambiguous, unmatched, underpaid, overpaid, late, or malformed payment cases.

## Assumptions

- [ASSUMPTION] The MVP ships inside existing Blesta client and admin responsive web surfaces, not as a standalone app or native mobile surface.
- [ASSUMPTION] The current Blesta Bootstrap/Paradigm theme and company theme settings supply the final visual theme values; KuickPay docs define semantic aliases and behavior.
- [ASSUMPTION] Customer-facing payment instructions are maintained through language files and admin-configured instruction groups, not hard-coded copy.
- [ASSUMPTION] Admin Voucher operations live in a plugin/admin extension surface if the architecture workflow chooses a companion plugin for reconciliation screens.
