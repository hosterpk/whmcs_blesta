## Decisions

### 2026-06-09 - Create BMad PRD from user-provided KuickPay/Blesta intake

- Decision: Produce a BMad-style PRD workspace with `prd.md`, `addendum.md`, reconciliation notes, and a reviewer note.
- Rationale: The provided intake contained PRD content, technical architecture notes, SQL/data-model detail, story breakdown, and implementation handoff text. BMad PRD discipline keeps product requirements in the PRD and moves implementation detail to the addendum.
- Outcome: `prd.md` is the canonical PRD; `addendum.md` preserves technical detail for architecture and story creation.

### 2026-06-09 - Treat product as launch/operational stakes

- Decision: Calibrate rigor for a customer payment integration, not a hobby or internal-only utility.
- Rationale: Incorrect payment posting, duplicate transactions, credential leakage, or reconciliation failure can affect customers and finance operations.
- Outcome: The PRD includes safety guardrails, reconciliation requirements, auditability, secret handling, Manual Review, rollout phases, risks, and open questions.

### 2026-06-09 - Use non-merchant gateway framing

- Decision: Define KuickPay as a Blesta non-merchant payment flow for v1.
- Rationale: Customers pay externally using a Consumer Number rather than entering payment credentials inside Blesta.
- Outcome: The PRD excludes card tokenization and Blesta-initiated recurring auto-charge.

### 2026-06-09 - Fail closed on payment truth

- Decision: Unknown, malformed, unmatched, or amount-mismatched KuickPay responses cannot mark invoices paid.
- Rationale: Payment processor responses are externally controlled and public docs expose generic result strings.
- Outcome: Parser fixtures, Manual Review, amount/reference validation, duplicate checks, and safe Payment Posting are central requirements.

### 2026-06-09 - Keep implementation detail in addendum

- Decision: Move SOAP field mappings, parser observations, data-model fields, extension tree, implementation sequence, and handoff prompt to `addendum.md`.
- Rationale: These details are valuable for implementation but would make the PRD read like a backlog or technical design.
- Outcome: Main PRD remains capability-focused with stable FR IDs.

### 2026-06-09 - Defer unresolved processor details to Open Questions

- Decision: Preserve unresolved KuickPay response-code, date-format, credential, fee, callback, rate-limit, partial payment, and cancellation questions as explicit Open Questions.
- Rationale: These are not safe to infer before live/sandbox validation.
- Outcome: Phase 0 requires API contract validation before final Payment Posting logic.

### 2026-06-09 - Remove original intake after artifact creation

- Decision: Delete the user-provided intake artifact after the BMad PRD workspace is created and verified.
- Rationale: The user explicitly requested removal after the BMad-style PRD is created.
- Outcome: Completed after the PRD workspace passed source-name leakage, assumption-index, and text-hygiene checks.
